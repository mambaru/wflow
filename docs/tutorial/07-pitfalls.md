# 07. Ловушки: занятый пул и таймеры

Эта глава про ошибку, на которой спотыкаются очень часто — и студенты, и уже работающие разработчики.

Симптом звучит так: «Я поставил задание на выполнение через 2 секунды, а оно выполнилось через 4. Значит, таймер в библиотеке врёт?»

В большинстве случаев таймер ни при чём. Задание **вовремя попало в очередь**, но в нужный момент **некому было его исполнить**: все рабочие потоки были заняты другой долгой работой.

## Сначала ломаем специально

Откройте [`example11.cpp`](../../examples/example11.cpp):

```cpp
opt.threads = 4;
wflow::workflow wf(ios, opt);
wf.start();

// четыре долгих задания — по одному на каждый поток пула
for (int i=0; i < 4; ++i)
  wf.post([](){ sleep(4);});

// «разбуди меня через 2 секунды»
wf.safe_post(
  std::chrono::seconds(2),
  [&ios, beg]()
  {
    std::cout << "It was expected 2 seconds, but waited "
              << time(nullptr) - beg << " seconds" << std::endl;
    ios.stop();
  });
```

Что происходит по времени:

1. В момент старта четыре потока пула сразу получают по `sleep(4)` и засыпают на четыре секунды.
2. Через две секунды отложенное задание **становится готовым** — его можно выполнять.
3. Но свободного потока нет: все четверо ещё спят. Задание ждёт в очереди.
4. Примерно через четыре секунды один поток освобождается, подхватывает отложенное задание — и вы видите «ждало ~4 секунды».

Отсюда важное различение, которое стоит запомнить надолго:

* **время постановки / готовности** — когда задание имеет право начать выполняться;
* **время фактического старта** — когда нашёлся исполнитель.

В однопоточном учебном примере с крошечными лямбдами эти моменты почти совпадают. В пуле с долгими handler'ами — нет.

## Как лечат: разделяют очереди по роли

Идея простая: тяжёлую работу и «короткие, но срочные» вещи не стоит кормить из одной и той же маленькой бригады потоков.

[`example12.cpp`](../../examples/example12.cpp) делает именно это. Большой пул забирает долгие `sleep`, а отложенное критичное задание ставится в **другой** `workflow` на том же `io_context`, без конкуренции за эти же четыре (или десять) занятых потоков:

```cpp
opt.threads = 10;
wflow::workflow wf(ios, opt);   // тяжёлая работа

opt.threads = 0;
wflow::workflow wf2(ios, opt);  // лёгкая очередь для дедлайнов
wf.start();

for (int i=0; i < 10; ++i)
  wf.post([](){ sleep(4);});

wf2.safe_post(std::chrono::seconds(2), /* печать и ios.stop() */);
```

Если запустить и замерить время, ожидание снова оказывается около двух секунд: «будильник» не стоял в одной очереди с десятью сонями.

Тот же приём используют в сервисах: отдельно пул для бизнес-обработки, отдельно — для служебных тиков, таймаутов протокола, принудительного останова.

## Правила, которые стоит унести с собой

1. Не кладите долгий блокирующий код (`sleep`, синхронный тяжёлый I/O, долгий CPU без пауз) в общий пул, если на него же завязаны обязательные по времени действия.
2. Критичное по задержке — на отдельный лёгкий workflow или с явным запасом свободных потоков под худший случай.
3. Для очень лёгких заданий большой пул часто вреден: см. замеры в [`example09`](../../examples/example09.cpp) и [`example10`](../../examples/example10.cpp).

Если в лабораторной у вас «таймер иногда опаздывает», прежде чем искать баг в библиотеке, проверьте: а не заняты ли все исполнители вашей же работой.
