# 08. Цепочки запросов и конфиг из файла

Пока что задания у нас были разовыми: положили в очередь — выполнили — забыли. В реальных системах часто нужен **диалог**: отправили запрос, дождались ответа, из ответа собрали следующий запрос, и так далее. Например, опрос устройства, постраничная выгрузка, повторы до успеха или до лимита попыток.

Вручную это можно собрать из `post` и колбэков, но легко утонуть в запутанных лямбдах. В wflow для такого сценария есть готовая конструкция — **requester**.

## Из чего состоит requester

Вы описываете три роли.

1. **Отправитель (sender).** Получает запрос, запускает асинхронную работу (сеть, другой workflow, что угодно) и когда ответ готов — вызывает переданный колбэк.
2. **Генератор (generator).** Смотрит на предыдущий ответ и решает, что делать дальше. В самом начале ответа ещё нет — генератору передают «пустой» старт, и он создаёт первый запрос. Если цепочку пора закончить — возвращает пустой указатель.
3. **Период.** С каким ритмом такие диалоги вообще заводятся (например, раз в секунду начинать новый цикл опроса).

Пока это звучит абстрактно — смотрите код.

## Простой случай: один шаг

[`example13.cpp`](../../examples/example13.cpp) делает цепочку из одного запроса. «Сеть» эмулируется задержкой на полсекунды через тот же workflow:

```cpp
bool sender(request::ptr, response::handler callback)
{
  wf.post(std::chrono::milliseconds(500), [callback]()
  {
    std::cout << "response ready" << std::endl;
    callback( response::ptr(new response() ));
  });
  return true;
}

request::ptr generator(response::ptr resp)
{
  if ( resp == nullptr )
  {
    std::cout << "generate first" << std::endl;
    return request::ptr(new request() );
  }
  std::cout << "finish chain" << std::endl;
  return nullptr;   // цепочка закончена
}

wf.create_requester<request, response>(std::chrono::seconds(1), sender, generator );
ios.run();
```

Как читать поток событий:

1. Раз в секунду requester просит генератор начать цепочку (`resp == nullptr`) — печатается `generate first`.
2. Sender «ходит в сеть» 500 мс и вызывает колбэк с ответом — `response ready`.
3. Генератор получает ответ, понимает, что продолжать нечего, и возвращает `nullptr` — `finish chain`.
4. Через секунду всё повторяется.

Запустите пример и подержите несколько секунд: в консоли будет ровное дыхание generate → response → finish.

## Сложнее: обрыв и повтор

[`example14.cpp`](../../examples/example14.cpp) уже похож на учебный автомат состояний: длинная цепочка шагов, искусственная ошибка на середине, старт сначала, несколько успешных проходов и останов.

Прежде чем читать весь файл целиком, нарисуйте на бумаге состояния: «старт», «шаг N», «ошибка», «повтор», «финиш». Потом сопоставьте рисунок с ветками генератора — так requester перестаёт казаться магией.

## Настройка из JSON без перекомпиляции

Жёстко прошивать число потоков и лимиты в `.cpp` неудобно: каждое изменение — сборка заново. [`example15.cpp`](../../examples/example15.cpp) показывает другой путь: опции workflow читаются из JSON-файла.

Без аргументов программа печатает «паспорт» значений по умолчанию — удобно посмотреть, какие поля вообще бывают. С путём к файлу — загружает конфиг и гоняет строки из STDIN в STDOUT через настроенную очередь:

```cpp
wflow::workflow_options opt;
std::string err;
if ( !wflow::load(argv[1], &opt, &err) )
{
  std::cerr << "ERROR: " << err << std::endl;
  return -1;
}
wflow::workflow wf(ios, opt);
wf.start();
```

Примеры запуска:

```bash
./example15
time cat examples/example15.cpp | ./example15 examples/example15-1.json
```

Попробуйте поменять в JSON число потоков или ограничения и сравнить время прогона одной и той же ленты данных. Так быстрее нащупывается чувство «как опции влияют на поведение», чем бесконечными правками исходника.

Если поддержка JSON в вашей сборке отключена — смотрите флаги в главном Readme.
