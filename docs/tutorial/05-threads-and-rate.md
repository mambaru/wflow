# 05. Потоки и скорость

До этой главы можно было жить с одной мыслью: «есть очередь и есть цикл, который её крутит». Теперь добавим два рычага, которыми в сервисах пользуются постоянно: **свой пул потоков** и **ограничение скорости обработки**.

## Один поток цикла или несколько рабочих

Если `threads = 0`, задания выполняются там же, где крутится ваш `io_context` — часто это один поток с `ios.run()`. Это простой режим: меньше гонок, проще рассуждать о порядке.

Если `threads = N > 0`, workflow поднимает N рабочих потоков. Их нужно запустить через `start()`. Тогда несколько заданий из очереди могут выполняться одновременно.

Пример — [`example06.cpp`](../../examples/example06.cpp):

```cpp
wflow::workflow_options opt;
opt.threads = 5;
wflow::workflow wf(opt);
wf.start();
for (int i = 0; i < 100; ++i)
  wf.post( std::bind(task, i));
```

Внутри `task` есть короткая случайная пауза и печать идентификатора потока. На выводе видно, что номера заданий идут не строго по порядку, а `thread_id` меняется — пул реально работает.

Когда пул окупается:

* задания **ждут** внешний ресурс (сеть, диск, другой сервис) и могут пересекаться по времени;
* задания делают заметную CPU-работу и имеют смысл на нескольких ядрах.

Когда пул часто **не** помогает:

* handler крошечный (увеличил счётчик, положил байт в буфер);
* узкое место — общая блокировка или сама очередь, а не нехватка потоков.

Интуиция «чем больше потоков, тем быстрее» для учебных микрозаданий обычно ломается. Это нормально и как раз то, что показывают бенчмарки ниже.

## Скорость обработки (rate limit)

Лимит размера очереди отвечает на вопрос: «сколько можно *держать в памяти*?»  
Ограничение скорости — на другой: «сколько можно *выполнять в единицу времени*?»

Даже если памяти хватает, долбить базу или соседний сервис тысячами запросов в секунду бывает нельзя. Тогда задают `rate_limit`.

В [`example07.cpp`](../../examples/example07.cpp) стоит предел «примерно 10 заданий в секунду» при пяти потоках:

```cpp
opt.threads = 5;
opt.rate_limit = 10;
wflow::workflow wf(ios, opt);
wf.start();
for (int i = 0; i < 100; ++i)
  wf.post( [&, i](){
    std::lock_guard<std::mutex> lk(m);
    std::cout << i << " " << std::this_thread::get_id() << std::endl;
  });
wf.shutdown();
wf.wait();
```

Запустите и посмотрите на время работы программы: сто заданий при лимите 10/с не закончатся мгновенно. Часть первых заданий проходит сразу (в пределах текущего окна), остальные библиотека придерживает, чтобы не выйти за скорость.

В реальном сервисе `maxsize` и `rate_limit` часто живут вместе: очередь не бесконечна, и обработчик не разгоняется без договора с бэкендом.

## Сколько потоков «правильно»?

Ответ без замера почти всегда неверный. Поэтому в комплекте есть два бенчмарка:

* [`example09.cpp`](../../examples/example09.cpp) — много лёгких `post` (возможны потери при маленькой очереди);
* [`example10.cpp`](../../examples/example10.cpp) — то же через `safe_post` (потерь из‑за размера нет).

Число потоков обычно передаётся аргументом командной строки. На лёгких заданиях типичная картина такая:

* 0–1 поток — часто **максимальный** throughput;
* 2 и больше — растут накладные расходы на синхронизацию, скорость падает;
* у `post` появляются drops, когда производитель быстрее потребителя.

Упражнение: прогоните `example09` с 0, 1, 2, 4, 8 потоками, запишите результаты. Затем честно сравните со своей задачей: ваш handler ближе к «пустой лямбде» или к ожиданию сети? Пул имеет смысл во втором случае.
