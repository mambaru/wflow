# 02. Обычная и защищённая постановка

Представьте сервис, который принимает события быстрее, чем успевает их обрабатывать. Очередь растёт. Рано или поздно приходится решить: **что делать с новыми заданиями, когда места уже нет?**

В wflow на этот вопрос отвечают два разных метода постановки.

## Два контракта

**Обычная постановка** — `post`. Если очередь переполнена, задание могут **не принять**. Для программы это ожидаемое поведение: вы либо получаете отказ (и можете среагировать), либо просто теряете часть работы. Так делают для потока, который можно проредить: свежие метрики важнее старых, лишний кадр видео можно выбросить, повторный «пинг» не критичен.

**Защищённая постановка** — `safe_post`. Из‑за лимита размера такое задание **не выбрасывают**. Его используют для вещей, которые нельзя «забыть, потому что было тесно»: остановить сервис, ответить клиенту, освободить ресурс, выполнить обязательный служебный шаг.

Оба метода умеют два режима по времени:

* выполнить как можно скорее;
* выполнить не раньше чем через заданный интервал (или в конкретный момент времени).

Базовые «пустые» сценарии без переполнения:

* [`example01.cpp`](../../examples/example01.cpp) — несколько `safe_post`;
* [`example02.cpp`](../../examples/example02.cpp) — то же через обычный `post`.

Пока очередь не полная, разницы в результате почти не видно. Разница проявляется именно под давлением.

## Что происходит при переполнении

Развёрнутый пример — [`example03.cpp`](../../examples/example03.cpp). Там очередь намеренно крошечная: в опциях стоит `maxsize = 5`, а программа пытается положить **десять** заданий подряд.

У `post` есть удобная перегрузка с двумя обработчиками. Первый — то, что должно выполниться, если задание приняли. Второй — что сделать, если места нет (его как раз и называют drop-обработчиком):

```cpp
wflow::workflow_options opt;
opt.maxsize = 5;
wflow::workflow wf(ios, opt);

for (int i = 0; i < 10; ++i)
{
  wf.post(
    [i](){ std::cout << "post " << i << std::endl; },
    [i](){ std::cout << "drop " << i << std::endl; }
  );
}

std::cout << "Run!" << std::endl;
ios.run();
```

Как читать этот код.

1. Цикл ещё **до** `ios.run()` пытается поставить десять заданий.
2. Первые пять помещаются в очередь — для них позже напечатается `post N`.
3. Остальные пять в очередь не попали — для них сразу вызывается второй обработчик и печатается `drop N`.
4. Только потом программа пишет `Run!` и запускает цикл, который выполняет принятые задания.

Важно: отказ здесь — не авария и не «баг библиотеки». Это выбранная политика. В реальном сервисе во втором обработчике можно увеличить счётчик потерь, записать в лог, отправить метрику — лишь бы вы понимали, что часть работы сознательно не принята.

Если бы вместо `post` стоял `safe_post`, лимит размера не стал бы причиной выброса: критичные задания всё равно остались бы в системе (ценой роста потребления памяти, если так делать бездумно со всем подряд).

## Как выбирать на практике

Ориентир для учебных и первых рабочих проектов:

| Ситуация | Что ставить |
|----------|-------------|
| Поток данных, который можно проредить | `post` |
| Ответ клиенту, останов, освобождение ресурса | `safe_post` |
| Heartbeat / «обязательно раз в N секунд» | чаще `safe_post` или отдельный лёгкий workflow |
| Не уверены | спросите себя: «если это задание исчезнет под нагрузкой, система останется корректной?» Если нет — защищённая постановка |

Подробнее про сам лимит очереди — в [следующей главе](03-queue-limits.md).

## Боковой эффект: потоки и скорость

Отдельно полезно посмотреть [`example10.cpp`](../../examples/example10.cpp): там много лёгких `safe_post` при разном числе потоков. Потерь нет (всё защищённое), но скорость на «пустых» заданиях часто падает, когда потоков слишком много — они мешают друг другу на общих структурах очереди.

Мораль на будущее: выбор `post` / `safe_post` решает вопрос **корректности под переполнением**, а число потоков — вопрос **производительности**. Это разные оси настройки; «просто добавим потоков» не заменяет правильный контракт постановки.
