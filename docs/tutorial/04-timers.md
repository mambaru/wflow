# 04. Таймеры

До сих пор мы ставили разовые задания: «сделай сейчас» или «сделай через N секунд». Часто нужно другое: **повторять действие по расписанию**, пока сервис жив — проверять состояние, слать heartbeat, подметать временные файлы, опрашивать соседний компонент.

Для этого у workflow есть периодические таймеры. Вы задаёте интервал и обработчик. После каждого срабатывания обработчик возвращает `bool`:

* `true` — «продолжай, следующий тик по расписанию»;
* `false` — «хватит, этот таймер больше не нужен».

Пока вы возвращаете `true`, библиотека сама планирует следующий запуск. Это удобнее, чем вручную каждый раз ставить новое отложенное задание из предыдущего.

## Разбор example05

Откройте [`example05.cpp`](../../examples/example05.cpp). Там одновременно живут таймер и несколько разовых отложенных сообщений:

```cpp
wf.create_timer(
  std::chrono::milliseconds(500),   // первая задержка
  std::chrono::milliseconds(1000),  // дальше — раз в секунду
  []()->bool
  {
    static int count = 4;
    std::cout << "timer count=" << count << std::endl;
    return --count != 0;            // на нуле вернём false и остановимся
  }
);

wf.post( std::chrono::seconds(3), [](){ std::cout << "after 3 seconds " << std::endl; });
wf.post( [](){ std::cout << "first message " << std::endl; } );
ios.run();
```

Что здесь важно понять.

* Первое задание без задержки (`first message`) почти наверняка напечатается раньше всех — оно уже готово к выполнению.
* Таймер сначала ждёт 500 мс, потом тикает примерно раз в секунду и сам гаснет после нескольких итераций.
* Разовые `post` с задержкой 1–4 секунды вклиниваются между тиками. На выводе получается «перемешанная» картина во времени — так и должно быть: это одна очередь событий, а не несколько независимых программ.

Похожий по духу сценарий есть в [`example16.cpp`](../../examples/example16.cpp) — имеет смысл прогнать оба и сравнить.

Интервал иногда задают строкой вроде `"1m20s"` (удобно для конфигов). В учебном коде чаще достаточно обычного `std::chrono`.

## Чего таймер не обещает

Фраза «каждые 100 миллисекунд» в асинхронной системе — это **намерение**, а не железный метроном.

Если ваш обработчик сам работает дольше интервала, следующий тик сдвинется. Если все рабочие потоки заняты тяжёлыми заданиями, тик вовремя попадёт в очередь, но **исполнится позже** — свободного потока нет. Эту ловушку специально разбирают в [главе 07](07-pitfalls.md) на паре [`example11`](../../examples/example11.cpp) / [`example12`](../../examples/example12.cpp).

Практический вывод для критичных вещей (останов, heartbeat, дедлайн по протоколу):

* не надейтесь, что тяжёлая очередь «сама подвинется»;
* ставьте такое защищённо и/или выносите на отдельный лёгкий workflow;
* не цепляйте к таймеру объекты, которые могут умереть раньше него, без явной защиты lifetime — см. [главу 09](09-owner.md) и [`example18.cpp`](../../examples/example18.cpp).
