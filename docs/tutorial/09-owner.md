# 09. Owner: отмена, lifetime и колбэки

Эта глава длиннее остальных — и это нормально. Очередь и таймеры без правильного lifetime почти неизбежно дают use-after-free при останове. **Owner** — основной инструмент wflow для этой проблемы.

Примеры к главе:

| Пример | Тема |
|--------|------|
| [`example18.cpp`](../../examples/example18.cpp) | `wrap` + `reset` — остановили объект |
| [`example19.cpp`](../../examples/example19.cpp) | `tracking` — закрыли соединение |
| [`example20.cpp`](../../examples/example20.cpp) | `callback` — один вызов / два / ни одного |

Формальные проверки — в [`tests/owner/owner_test.cpp`](../../tests/owner/owner_test.cpp).

---

## Зачем это нужно

В синхронном коде объект живёт, пока выполняется его метод. В асинхронном — иначе:

1. Объект сервиса кладёт в очередь лямбду с захватом `this`: «через секунду вызови мой метод».
2. Через 200 мс сервис останавливают и уничтожают.
3. Через секунду очередь всё равно вызывает лямбду.
4. Лямбда лезет в уже освобождённую память → use-after-free.

Симптом обычно противный: «иногда падает при shutdown», «валится под нагрузкой при реконнекте клиентов». Отладка дорогая, потому что между постановкой и вызовом проходит время и, возможно, другой поток.

**Owner не удаляет задания из очереди workflow.** Он делает другое: к моменту вызова проверяет, «актуален ли ещё этот lifetime», и либо выполняет основной код, либо уходит в запасную ветку (или тихо ничего не делает).

Workflow сам по себе **не знает**, жив ли ваш C++-объект. Контракт lifetime — на стороне приложения, через owner.

---

## Как это устроено (идея, не API-справочник)

У owner внутри есть токен поколения — по сути `shared_ptr` на пустой объект-маркер. Когда вы делаете `wrap`, в обёртку кладётся `weak_ptr` на этот токен.

При вызове обёртки:

* если `weak_ptr` ещё можно «поднять» (`lock` успешен) — токен жив → вызывается **основной** handler;
* если поднять нельзя — токен уже уничтожили → вызывается **альтернативный** handler (или пустой результат, если альтернативы нет).

Метод `reset()` **не обнуляет** токен в смысле «сделать nullptr навсегда». Он **подменяет** токен на новый: старые обёртки держат `weak_ptr` на старый объект и видят его протухшим; новые `wrap` после `reset` уже привязаны к новому поколению и снова работают.

Отсюда важное следствие:

* `reset()` — это «все **старые** обёртки больше не выполняют основную работу»;
* сам объект `owner` при этом жив, и им можно пользоваться дальше;
* очередь workflow по-прежнему может содержать старые обёртки — они просто безвредны (идут в alt).

Для соединений картина похожа, но токен один на `io_id` (см. раздел про tracking).

## wrap и reset: остановили объект

Это базовый сценарий. Разбор — [`example18.cpp`](../../examples/example18.cpp).

У сервиса есть owner и состояние. Он ставит два отложенных тика через `wrap`. Между ними вызывается `stop()` → `reset()`:

```cpp
struct service
{
  wflow::owner own;
  int value = 0;

  void schedule(wflow::workflow& wf, std::chrono::milliseconds delay)
  {
    wf.safe_post(delay, own.wrap(
      [this]()
      {
        ++value;
        std::cout << "tick #" << value << " value=" << value << std::endl;
      },
      [this]()
      {
        std::cout << "skipped (owner reset), value was " << value << std::endl;
      }
    ));
  }

  void stop()
  {
    own.reset();
    std::cout << "service stopped" << std::endl;
  }
};
```

В `main` примерно такая шкала времени:

| Время | Что происходит |
|-------|----------------|
| 0 | поставлены тики на 100 мс и 300 мс, останов на 200 мс |
| ~100 мс | первый тик: токен жив → `tick #1` |
| ~200 мс | `reset()` — старое поколение протухло |
| ~300 мс | второй тик: токен мёртв → `skipped ...` |

Роли аргументов `wrap`:

* **первый** — основной код, пока lifetime актуален;
* **второй** — что делать, если уже был `reset` (лог, метрика, тихий skip). Можно передать `nullptr`: тогда при протухшем токене основной код не вызывается, возвращается значение по умолчанию для типа результата.

Что `reset` **не** делает:

* не удаляет задания из workflow;
* не уничтожает ваш `service` автоматически;
* не отменяет «будущие» `wrap`, которые вы сделаете *после* reset — они привяжутся к новому поколению.

Типичный порядок останова компонента:

1. Перестать принимать новую внешнюю работу.
2. Вызвать `own.reset()`.
3. Дать очереди доработать: старые обёртки сходят в alt и не трогают разрушаемое состояние.
4. Уже потом уничтожать объект (или полагаться на то, что поля после reset больше не читает основной handler).

В примере 18 объект специально держат через `shared_ptr` до конца `run()`, а альтернативная ветка ещё читает `value` — это учебный вывод «нас скипнули». В боевом коде в alt часто **не** ходят в поля останавливаемого объекта: пишут в лог/метрики с захваченными по значению данными или делают пустой handler.

## tracking: закрыли соединение, а не весь сервис

Иногда «жив» не весь процесс и не весь сервисный объект, а **конкретный клиент**. Соединение `io_id = 42` закрылось; в очереди ещё лежат задания «для него». Выполнять их бессмысленно или даже вредно (ответ в никуда, работа с чужим контекстом).

Для этого у owner есть **tracking** — отдельный токен на каждый `io_id`.

Сначала tracking нужно **включить**:

```cpp
own.enable_tracking(true);
```

Пока флаг выключен, `tracking(io_id, ...)` ведёт себя как обычный `wrap` по общему lifetime owner'а и **ничего не пишет** в map соединений. Это важно: забыли `enable_tracking(true)` — отдельной отмены по клиенту не будет.

Разбор — [`example19.cpp`](../../examples/example19.cpp):

```cpp
own.enable_tracking(true);
const wflow::owner::io_id_t conn_id = 42;

wf.safe_post(std::chrono::milliseconds(50), own.tracking(
  conn_id,
  [](){ std::cout << "conn 42: request handled" << std::endl; },
  [](){ std::cout << "conn 42: cancelled early" << std::endl; }
));

wf.safe_post(std::chrono::milliseconds(150), own.tracking(
  conn_id,
  [](){ std::cout << "conn 42: late work" << std::endl; },
  [](){ std::cout << "conn 42: cancelled (client gone)" << std::endl; }
));

wf.safe_post(std::chrono::milliseconds(100), [&own, conn_id]()
{
  own.release_tracking(conn_id);
  std::cout << "conn 42 closed" << std::endl;
});
```

По времени:

1. ~50 мс — токен соединения ещё в map → основный handler.
2. ~100 мс — `release_tracking(42)` удаляет токен из map.
3. ~150 мс — обёртка видит протухший `weak_ptr` → альтернатива `cancelled`.

### Правила, без которых tracking ломается в голове

1. **Создавайте обёртки до `release_tracking`.**  
   Оба `tracking(conn_id, ...)` в примере сделаны заранее и делят один токен. Если вызвать `tracking(42, ...)` *после* release, библиотека может создать **новый** токен для того же номера — и «закрытие старого клиента» на него не подействует.

2. **Всегда вызывайте `release_tracking` при закрытии соединения.**  
   Иначе map будет расти: каждый новый `io_id` оставляет запись. Это уже утечка логических ресурсов.

3. **`enable_tracking(false)` очищает всю map.**  
   Все старые tracking-обёртки после этого уходят в alt при вызове. Имеет смысл при глобальном останове, но не как замена точечному `release_tracking`.

4. **`tracking_size()`** показывает, сколько соединений сейчас «висят» в map — удобно для отладки и тестов.

5. **`reset()` owner'а** инвалидирует общий lifetime (и обычный `wrap`/`callback`). Tracking-токены в map — отдельная история: их снимают через `release_tracking` / `enable_tracking(false)`. В сложных остановах часто делают и то, и другое: сбросили сервис + почистили соединения.

## callback: ответ должны вызвать ровно один раз

Сетевой и асинхронный код полон колбэков вида «когда ответ будет готов — вызови это». На практике случаются три ошибки:

1. **Вызвали дважды** (баг на той стороне, повторная доставка, гонка).
2. **Не вызвали никогда** (забыли ветку ошибки, early return).
3. **Вызвали уже после того, как ваш объект остановили** (`reset`).

`owner::callback` как раз про эти контракты. Пример — [`example20.cpp`](../../examples/example20.cpp).

```cpp
wflow::owner own;
own.set_double_call_handler([](){
  std::cout << "double-call detected" << std::endl;
});
own.set_no_call_handler([](){
  std::cout << "no-call: callback destroyed without invoke" << std::endl;
});

auto cb = own.callback([](int v){
  std::cout << "ok: result=" << v << std::endl;
});
cb(42);   // норма
cb(99);   // уже не выполнит основной код → double_call_handler
```

И отдельно — уничтожили колбэк, так и не вызвав:

```cpp
{
  auto cb = own.callback([](int){ /* ... */ });
  // забыли cb(...)
} // при уничтожении последнего владельца control → no_call_handler
```

### Как это читать

* Все копии одного и того же `callback(...)` делят общее состояние «уже вызывали?».
* Первый успешный вызов (и только если owner ещё жив) выполняет ваш handler.
* Повторный вызов не выполняет handler повторно; если задан `set_double_call_handler` — зовёт его (удобно для лога/ассерта/метрики).
* Если колбэк уничтожили **без единого вызова**, при разрушении контрольного блока срабатывает `set_no_call_handler` — «ответа так и не было».
* После `own.reset()` вызов `callback` **не** выполняет основной handler (так же, как `wrap`). Это проверено тестами: lifetime owner важнее «нам прислали ответ».

`callback` можно комбинировать с `wrap`/`tracking`: сначала обернули ответ в `callback`, потом в tracking по `io_id`, чтобы и «один раз», и «только пока клиент на линии». В тестах есть такие связки; в учебных примерах 18–20 они разведены по отдельности, чтобы проще читать.

## Как стыковать с workflow на практике

Минимальный рабочий шаблон для класса-сервиса:

```cpp
class my_service
{
public:
  explicit my_service(wflow::workflow& wf) : _wf(wf) {}

  void start()
  {
    _wf.create_timer(std::chrono::seconds(1), _own.wrap(
      [this]() -> bool {
        this->on_tick();
        return true;          // продолжать, пока не reset
      },
      []() -> bool { return false; } // после reset таймер гасим
    ));
  }

  void on_request(/* ... */)
  {
    _wf.post(_own.wrap(
      [this](){ this->handle(); },
      [](){ /* skip */ }
    ));
  }

  void stop()
  {
    _own.reset();   // всё старое становится безвредным
  }

private:
  wflow::workflow& _wf;
  wflow::owner _own;
  void on_tick();
  void handle();
};
```

Правила стыковки:

1. Owner обычно **член** того объекта, чей lifetime защищаете (или отдельный объект на соединение).
2. В очередь и на таймеры уходит **результат** `wrap` / `tracking` / `callback`, а не голый `[this]{...}`.
3. При останове сначала `reset` (и `release_tracking` для открытых соединений), потом разрушение полей, на которые смотрел основной handler.
4. `safe_post` решает «не потерять из‑за maxsize»; owner решает «не выполнить, если объект уже неактуален». Это **разные** оси — часто нужны обе.

## Частые ошибки студентов

1. **Захватили `this` в лямбду и не обернули.**  
   Owner лежит в классе «на будущее», а в `post` уходит голый захват — защиты нет.

2. **Думают, что `reset` чистит очередь.**  
   Нет. Очередь как была, так и осталась; изменилось поведение обёрток при вызове.

3. **В alt после `reset` продолжают пользоваться полуразрушенным объектом.**  
   Alt должен быть безопасен в момент останова. Лучше захватывать в лямбду копии нужных скаляров или не трогать `this`.

4. **Tracking без `enable_tracking(true)`.**  
   Код «вроде с io_id», а отмены по клиенту нет.

5. **`tracking` после `release_tracking` на тот же id.**  
   Получаете новый токен и удивляетесь, почему «отменённое» всё же выполнилось.

6. **Не вызывают `release_tracking` при закрытии сокета.**  
   Map растёт вместе с числом клиентов за время жизни процесса.

7. **Путают `post`/`safe_post` с owner.**  
   Переполнение очереди и протухший lifetime — разные проблемы. Защищённая постановка не заменяет `wrap`.
