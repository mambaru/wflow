# 01. Первые шаги

В синхронной программе вы вызываете функцию — и она выполняется прямо сейчас, в текущем потоке. В серверах и сетевых приложениях так часто нельзя: пока вы ждёте ответа или крутите долгий расчёт, всё остальное «встаёт». Поэтому работу ставят в очередь: «сделай это, когда будет можно» или «сделай через секунду».

**wflow** как раз про такую постановку. С его помощью обычно решают несколько задач сразу:

* положить работу в очередь и не думать, в каком потоке она выполнится прямо сейчас;
* выполнить её немедленно или с задержкой;
* не дать очереди разрастись без предела;
* запускать периодические действия (таймеры);
* при необходимости выделить несколько рабочих потоков под эту очередь.

Центральный объект библиотеки — `workflow`. Он живёт рядом с вашим `boost::asio::io_context`: цикл крутит события, workflow хранит и выдаёт задания.

## Минимальная программа

Хорошая точка входа — [`example01.cpp`](../../examples/example01.cpp) (защищённая постановка) и почти такой же [`example02.cpp`](../../examples/example02.cpp) (обычная). Смысл один и тот же:

```cpp
boost::asio::io_context ios;
wflow::workflow wf(ios);

// выполнить как можно скорее
wf.safe_post( [](){ std::cout << "Simple safe post  " << std::endl; } );

// выполнить примерно через 4 секунды
wf.safe_post( std::chrono::seconds(4), [](){
  std::cout << "Safe post after delay 4 second " << std::endl;
});

// крутим цикл, пока есть работа
ios.run();
```

Разберём по шагам, что происходит.

1. **`io_context`** — движок. Сам по себе он ничего полезного не делает, пока вы не вызовете `run()` (или аналог).
2. **`workflow`** привязывается к этому движку и получает очередь, куда можно класть лямбды и другие вызываемые объекты.
3. **`safe_post`** кладёт задание в очередь. Первый вызов — «сейчас» (как только цикл до него дойдёт), второй — «не раньше чем через 4 секунды».
4. **`ios.run()`** запускает цикл. Он забирает готовые задания и вызывает их. Когда работы не осталось, `run()` завершается, и программа выходит.

В этом режиме у workflow **нет собственного пула потоков**. Всё выполняется в том потоке, где вы вызвали `run()`. Для учебных примеров и многих однопоточных сервисов этого достаточно: отдельно «стартовать» workflow не нужно.

Запустите `example01` и посмотрите на порядок строк: сначала ближайшие задания, потом те, что с задержкой. Это нормально — очередь живёт во времени, а не только «в столбик».

## Когда появляется свой пул потоков

Если заданий много и они реально могут идти параллельно (ждут сеть, считают что‑то тяжёлое), одного потока цикла может не хватить. Тогда в опциях задают число потоков больше нуля. У workflow появляется **свой пул**, и его нужно явно запустить.

См. [`example06.cpp`](../../examples/example06.cpp):

```cpp
wflow::workflow_options opt;
opt.threads = 5;
wflow::workflow wf(opt);
wf.start();
for (int i = 0; i < 100; ++i)
  wf.post( std::bind(task, i));
```

Здесь создаётся пять рабочих потоков, они начинают разбирать очередь. В выводе вы увидите разные `thread_id` — значит, задания действительно разошлись по потокам.

Запомните простое правило:

* **`threads = 0`** (по умолчанию) — работаем на том `io_context`, который передали в конструктор; цикл крутите сами (`ios.run()`).
* **`threads = N > 0`** — свой пул; после создания вызываете `start()`, а при завершении программы согласованно останавливаете workflow и цикл.

Подробнее про потоки и про то, что «больше потоков» не всегда значит «быстрее», — в [главе 05](05-threads-and-rate.md).

## Два режима очереди (можно отложить)

По умолчанию отложенные задания живут во внутренней очереди библиотеки. Есть и режим ближе к «чистому» Asio. Для прохождения курса хватает режима по умолчанию. Если позже захочется сравнить скорость — смотрите [`example17.cpp`](../../examples/example17.cpp).
