# 03. Ограничение очереди

Если принимать задания без ограничений, при всплеске нагрузки очередь может вырасти до размеров всей оперативной памяти. Процесс начнёт тормозить, система — свопить, в худшем случае сервис убьёт OOM killer. Поэтому у workflow есть **потолок**: сколько заданий разрешено держать «в ожидании».

Когда потолок достигнут, обычная постановка (`post`) начинает отказывать — мы это уже видели в прошлой главе. Кроме жёсткого лимита обычно есть и «жёлтая зона»: порог, после которого библиотека может писать предупреждение в лог. Так вы узнаёте о проблеме раньше, чем очередь упрётся в максимум.

В учебных примерах лимит специально делают крошечным (5–10), чтобы поведение было видно сразу. В настоящем сервисе значения по умолчанию гораздо больше — десятки и сотни тысяч. Но смысл тот же: предел должен быть, и вы должны понимать, что происходит при его достижении.

## Немедленные задания и переполнение

Полный текст — [`example03.cpp`](../../examples/example03.cpp). Кратко идея:

```cpp
opt.maxsize = 5;
wflow::workflow wf(ios, opt);

for (int i = 0; i < 10; ++i)
{
  wf.post(
    [i](){ std::cout << "post " << i << std::endl; },
    [i](){ std::cout << "drop " << i << std::endl; }
  );
}
std::cout << "Run!" << std::endl;
ios.run();
```

Обратите внимание на порядок в выводе: сначала несколько строк `drop`, потом `Run!`, потом `post`. Это значит, что решение «принять / отбросить» принимается **в момент постановки**, ещё до запуска цикла. Цикл потом лишь выполняет то, что уже лежит в очереди.

Попробуйте сами:

1. Поставьте `maxsize = 100` — drops должны исчезнуть.
2. Уберите второй обработчик и смотрите только на то, сколько раз напечатается `post`.
3. Замените часть вызовов на `safe_post` — эти задания перестанут пропадать из‑за размера (но очередь для них всё равно потребляет память).

## Отложить работу — не значит освободить место

Частая ошибка в рассуждении: «если я поставлю задания с задержкой, они же ещё не в работе — значит, очередь свободна». На практике отложенные задания тоже **занимают учётный слот**, пока ждут своего времени.

Это показывает [`example04.cpp`](../../examples/example04.cpp). Код почти как в примере 03, только у каждого `post` есть крошечная задержка:

```cpp
for (int i = 0; i < 10; ++i)
{
  wf.post(
    std::chrono::nanoseconds(1),
    [i](){ std::cout << "post " << i << std::endl; },
    [i](){ std::cout << "drop " << i << std::endl; }
  );
}
std::cout << "Run!" << std::endl;
ios.run();
```

Здесь `Run!` печатается раньше, а `drop` — уже после старта цикла: таймеры на постановку срабатывают, когда цикл крутится. Но итог тот же: часть заданий не принимается, потому что лимит размера учитывает и «будущую» работу.

Вывод для проектирования: откладывание меняет **когда** выполнится задание, но не отменяет вопрос **сколько** заданий система готова помнить.

## Три рабочих стратегии

Когда вы упираетесь в лимит, обычно выбирают одно из трёх (иногда комбинируют):

1. **Увеличить очередь**, если пики короткие, а обработчик в среднем успевает догнать. Это лечит редкие всплески, но не хроническую перегрузку.
2. **Допустить потери** (`post` + мониторинг drop), если важнее свежие данные, чем полный хвост устаревших.
3. **Ограничить скорость выполнения** (rate limit) — чтобы не копить гору в памяти, а равномерно переваривать поток. Об этом — [глава 05](05-threads-and-rate.md).

Хороший тон в курсовой или лабораторной: не просто «поставил maxsize», а объяснить, *какую* из стратегий вы выбрали и почему.
